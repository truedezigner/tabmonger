# TabMonger Growth Plan

TabMonger should grow by being genuinely useful, easy to try, and easy to recommend. The goal is sustainable open-source adoption—not intrusive promotion, fake engagement, or analytics inside the self-hosted app.

## Product promise

- The self-hosted dashboard and browser companions remain free, open source, account-free, and telemetry-free.
- `tabmonger.com` may collect small aggregate marketing-site counters, documented in `ANALYTICS.md` and the public privacy page.
- Community requests stay private until the owner approves a short public title.
- Contributions are optional and never unlock features.

## What success means

The primary measure is **successful installs that become repeat use**. The public site cannot see private app usage, so the practical funnel is:

1. Marketing-site visits.
2. General, macOS, Windows, and Linux app-download clicks.
3. Chrome/Brave/Edge and Firefox companion-download clicks.
4. GitHub visits, stars, forks, and release downloads.
5. Community votes, feedback, and support clicks.

Weekly review should compare totals with the prior seven and 28 days. Repeat a promotion only when it produces meaningful downloads or community activity, not merely page views.

## Built-in growth loops

1. **A useful new-tab companion.** Make Chrome, Brave, Edge, and Firefox setup increasingly simple.
2. **A shared household dashboard.** Explain the LAN workflow with concrete examples and a short demo.
3. **Community roadmap.** Let people vote, suggest ideas, and see what others value while keeping publication owner-reviewed.
4. **Open-source participation.** Keep focused issues and small contribution opportunities welcoming.
5. **Future shareable templates.** Export themes or layouts without private URLs, credentials, or local data.
6. **Future plugin gallery.** Showcase safe community-built widgets and integrations with an explicit review model.

## Twelve-week launch rhythm

### Weeks 1–2: establish the baseline

- Collect aggregate traffic, source, download, GitHub, support, poll, and feedback events.
- Verify the Windows, macOS, and Linux first-run paths on real machines.
- Record one short, honest video showing install, LAN sharing, and new-tab setup.
- Improve the GitHub README’s first screen and release notes using questions from real testers.

### Weeks 3–4: focused community launch

- Prepare a Show HN post, a self-hosted-community post, and one concise launch page.
- Ask for feedback instead of demanding stars or donations.
- Publish only with Jon’s approval; Friday never posts externally without approval.
- Compare each source by downloads and community actions, not raw visits alone.

### Weeks 5–8: remove onboarding friction

- Turn repeated setup questions into UI or documentation improvements.
- Pursue signed/browser-store distribution when the manual extension steps are the main drop-off.
- Add focused use-case pages only when they answer a real search intent: home lab dashboard, shared family start page, self-hosted new tab, or private LAN bookmarks.
- Ship small, visible releases with screenshots and plain-language changelogs.

### Weeks 9–12: compound what worked

- Repeat the two strongest distribution channels.
- Submit to reputable open-source and self-hosted directories.
- Test a Product Hunt launch only after onboarding and signed distribution are ready.
- Prototype one safe sharing loop: sanitized theme/layout templates or a reviewed plugin gallery.

## Weekly operating review

Every week, record:

- Page views and source mix.
- General, macOS, Windows, Linux, Chrome/Brave/Edge, and Firefox downloads.
- GitHub opens, stars, forks, and release downloads where public data is available.
- Poll votes, suggestions, support clicks, and feedback submissions.
- The top source by meaningful actions.
- One thing to repeat, one thing to improve, and one thing to stop.

The private LAN metrics page provides the site counters. A server-side weekly report is written under the protected deployment data directory. GitHub clone traffic is not available without a private owner token and is not required for the initial plan.

## Guardrails

- No fake user votes, reviews, stars, testimonials, or traffic.
- Project-owner starter votes must be clearly labeled.
- No email list or promotional message without explicit opt-in.
- No analytics in downloaded TabMonger or its extensions.
- No raw referrers, IP addresses, user agents, cookies, fingerprints, or visitor identifiers in the aggregate analytics store.
- No external post, launch, email, or paid campaign without Jon’s approval.

## Cost and expectations

The initial measurement and launch plan can run on the existing TabMonger server for effectively $0 additional infrastructure cost. Growth is experimental; no plan can guarantee virality. The practical target is a steadily improving install funnel and a small community that recommends TabMonger because it works well.
